Clínica Salud Integral — Normalización de la base de datos
1. Objetivo
Explicar cómo se organiza el modelo de datos para reducir duplicidad, evitar dependencias incorrectas y conservar la integridad de la información. El análisis se realiza sobre cinco entidades cuyos modelos Prisma son `Patient`, `Doctor`, `Specialty`, `Appointment` y `User`; las tablas físicas correspondientes son `patients`, `doctors`, `specialties`, `appointments` y `users`.
2. Primera Forma Normal (1FN)
Una tabla cumple 1FN cuando cada campo contiene un solo valor y no existen listas o grupos repetidos dentro de una columna.

En el modelo propuesto:
- Los nombres y apellidos se almacenan en atributos separados.
- Cada paciente, médico, especialidad, cita y usuario ocupa un registro independiente.
- Cada cita contiene una sola referencia a un paciente y una a un médico.
- Cada médico contiene una sola referencia a una especialidad.
- Los roles y estados se representan mediante valores enumerados, no mediante listas dentro de un campo.
Resultado: los atributos definidos son atómicos y no se almacenan colecciones de valores dentro de una misma columna.
3. Segunda Forma Normal (2FN)
Una tabla cumple 2FN cuando cumple 1FN y cada atributo no clave depende de la clave primaria completa.

En este modelo, las cinco tablas utilizan claves primarias simples de un solo atributo (id). Por ello, no existen claves primarias compuestas respecto de las cuales pudiera presentarse una dependencia parcial.

Las dependencias principales respecto de la clave primaria son:
- Patient.id determina los datos personales del paciente.
- Doctor.id determina los datos profesionales y las referencias del médico.
- Specialty.id determina el nombre de la especialidad.
- Appointment.id determina los datos y referencias de la cita.
- User.id determina el correo, el hash de contraseña y el rol de la cuenta.
Resultado: al utilizar claves primarias simples, los atributos de cada tabla dependen de la totalidad de su clave primaria; no hay dependencias parciales.
4. Tercera Forma Normal (3FN)
Una tabla cumple 3FN cuando cumple 2FN y sus atributos no clave dependen de la clave primaria, sin depender transitivamente de otros atributos no clave.

Las dependencias funcionales principales del modelo son:
Patient.id       → firstName, lastName, email, birthDate
Doctor.id        → firstName, lastName, specialtyId, userId
Specialty.id     → name
Appointment.id   → patientId, doctorId, scheduledAt, reason, status
User.id          → email, password, role
La separación de entidades evita las siguientes duplicidades y dependencias transitivas: 
- El nombre de la especialidad se almacena en Specialty, no se repite como texto en cada médico. Doctor conserva únicamente specialtyId como referencia.
- Los datos personales del paciente se almacenan en Patient, no se duplican en cada cita. Appointment conserva patientId.
- Los datos profesionales del médico se almacenan en Doctor, no se duplican en cada cita. Appointment conserva doctorId.
- Las credenciales y el rol se almacenan en User, separados de los datos profesionales del médico.
- `Doctor.userId` es una clave foránea opcional y única para vincular una cuenta existente; no copia los atributos del usuario en la tabla `doctors`.
Resultado: los atributos descriptivos permanecen en la entidad a la que pertenecen y las relaciones se resuelven mediante claves foráneas.
5. Resultado de la normalización
Tabla	Información almacenada
Patient (tabla `patients`)	Datos personales de los pacientes.
Doctor (tabla `doctors`)	Datos profesionales y referencia opcional a la cuenta de acceso.
Specialty (tabla `specialties`)	Catálogo de especialidades médicas.
Appointment (tabla `appointments`)	Fecha, motivo, estado y referencias al paciente y al médico.
User (tabla `users`)	Correo, hash de contraseña y rol de acceso.


El modelo queda organizado en cinco tablas y utiliza claves foráneas para relacionar los registros sin duplicar los datos descriptivos de otras entidades. Los modelos Prisma singulares se mapean a los nombres físicos plurales indicados arriba.

`patients.birth_date` representa una fecha de calendario y se almacena como `DATE` en PostgreSQL (`@db.Date` en Prisma). Los campos que representan instantes se almacenan como `timestamptz(3)` en PostgreSQL (`@db.Timestamptz(3)` en Prisma).
6. Conclusión
El modelo propuesto cumple los criterios estructurales de 1FN, 2FN y 3FN: atributos atómicos, ausencia de dependencias parciales debido al uso de claves primarias simples y separación de atributos para evitar dependencias transitivas. Esta estructura servirá como base para implementar el esquema mediante Prisma y PostgreSQL.
