# Clínica Salud Integral — Normalización de la base de datos

## 1. Objetivo

Describir la organización de las cinco entidades de `prisma/schema.prisma` y cómo sus relaciones evitan duplicar atributos descriptivos.

## 2. Primera Forma Normal (1FN)

Los atributos contienen valores atómicos. Cada paciente, médico, especialidad, cita y usuario ocupa un registro. Una cita referencia un solo paciente y un solo médico; un médico referencia una especialidad. Los roles y estados se restringen mediante enums.

## 3. Segunda Forma Normal (2FN)

Las cinco entidades tienen una clave primaria simple `id`, de tipo UUID (`String @id @default(uuid()) @db.Uuid`). No hay claves primarias compuestas que permitan dependencias parciales.

Dependencias principales:

```text
Patient.id     → firstName, lastName, email, birthDate, phone
Doctor.id      → firstName, lastName, professionalLicense, email, specialtyId
Specialty.id   → name
Appointment.id → patientId, doctorId, scheduledAt, reason, status
User.id        → email, passwordHash, role, doctorId
```

## 4. Tercera Forma Normal (3FN)

Los datos descriptivos se mantienen en su entidad y las relaciones se expresan mediante claves foráneas:

- El nombre de especialidad vive en `Specialty`; `Doctor` conserva `specialtyId`.
- Los datos del paciente viven en `Patient`; `Appointment` conserva `patientId`.
- Los datos profesionales viven en `Doctor`; `Appointment` conserva `doctorId`.
- Las credenciales y el rol viven en `User`. La vinculación opcional con un médico se expresa mediante `User.doctorId`, único y nullable; `Doctor.user` es la relación inversa de Prisma.

## 5. Correspondencia con PostgreSQL

La migración inicial crea las tablas `Patient`, `Doctor`, `Specialty`, `Appointment` y `User`. Los nombres de columnas conservan camelCase salvo el mapeo definido en Prisma: `Appointment.scheduledAt` se almacena en `Appointment.startAt`.

`Patient.birthDate` se almacena como `DATE`. `Appointment.scheduledAt` se almacena como `TIMESTAMPTZ(6)`. Las PK y FK son UUID. La migración crea índices de consulta para citas, pero no restricciones únicas compuestas para impedir citas simultáneas.

## 6. Estado de reglas adicionales

La regla aprobada que impide programar dos citas con el mismo instante para el mismo paciente o médico sigue siendo un requisito funcional. No debe atribuirse a la base de datos mientras no exista una restricción correspondiente en Prisma y en una migración.
