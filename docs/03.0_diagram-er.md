# Clínica Salud Integral — Diagrama entidad-relación

## 1. Objetivo

Representar las entidades, claves, relaciones y cardinalidades definidas en `prisma/schema.prisma` y en la migración inicial.

## 2. Diagrama entidad-relación

Los nombres del diagrama corresponden a los modelos/tablas PostgreSQL tal como los crea la migración. `Appointment.scheduledAt` se almacena en la columna física `startAt`.

```mermaid
erDiagram
    Specialty ||--o{ Doctor : clasifica
    Doctor ||--o{ Appointment : atiende
    Patient ||--o{ Appointment : solicita
    Doctor o|--o| User : se_vincula

    Patient {
        UUID id PK
        String firstName
        String lastName
        String email UK
        Date birthDate
        String phone nullable
    }

    Doctor {
        UUID id PK
        String firstName
        String lastName
        String professionalLicense UK
        String email nullable
        UUID specialtyId FK
    }

    Specialty {
        UUID id PK
        String name UK
    }

    Appointment {
        UUID id PK
        UUID patientId FK
        UUID doctorId FK
        DateTime scheduledAt "TIMESTAMPTZ(6), columna startAt"
        String reason nullable
        AppointmentStatus status
    }

    User {
        UUID id PK
        String email UK
        String passwordHash
        UserRole role
        UUID doctorId FK, UK, nullable
    }
```

## 3. Relaciones y cardinalidades

- **Specialty — Doctor (1:N):** cada médico pertenece a una especialidad; una especialidad puede tener varios médicos.
- **Patient — Appointment (1:N):** cada cita tiene un paciente; un paciente puede tener varias citas.
- **Doctor — Appointment (1:N):** cada cita tiene un médico; un médico puede tener varias citas.
- **User — Doctor (opcional 1:1):** `User.doctorId` es una FK opcional y única que referencia `Doctor.id`. La relación inversa del modelo Prisma es `Doctor.user`. Un usuario puede vincularse a como máximo un médico y cada médico a como máximo un usuario.

## 4. Restricciones del modelo implementado

- Todas las PK y FK usan UUID.
- `Patient.birthDate` es `DATE`; `Appointment.scheduledAt` es `TIMESTAMPTZ(6)` y su columna se llama `startAt`.
- La migración crea tablas `Patient`, `Doctor`, `Specialty`, `Appointment` y `User`; las columnas conservan camelCase salvo `Appointment.startAt`.
- Hay índices no únicos de agenda por médico, paciente y estado. No existen restricciones únicas compuestas de médico/instante o paciente/instante en la migración.
- La regla que prohíbe coincidencias exactas de citas se conserva como requisito aprobado pendiente de implementación; no se representa como restricción existente en este diagrama.
