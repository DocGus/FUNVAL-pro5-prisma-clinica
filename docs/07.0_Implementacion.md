# Clínica Salud Integral — Implementación

## 1. Objetivo

Documentar el proceso de implementación de Clínica Salud Integral, desde la preparación de la base de datos hasta las pruebas y entrega del proyecto.

Este documento funcionará como una bitácora técnica y progresiva. En cada etapa se registrarán las actividades realizadas, las decisiones técnicas, los archivos creados o modificados, los comandos ejecutados y las verificaciones efectuadas.

La documentación distinguirá entre:

- **Implementado:** funcionalidad desarrollada total o parcialmente; se indicará el alcance concreto.
- **Verificado:** funcionalidad comprobada mediante comandos o pruebas.
- **Pendiente:** actividad todavía no realizada. Una actividad implementada pero sin comprobación se marcará como implementada y pendiente de verificación.

### Etapa 3. Servidor, rutas base y errores

**Objetivo:** completar la base ejecutable de Express, la documentación OpenAPI y el manejo global de errores.

**Depende de:** etapa 2.

**Estado inicial:** `src/app.ts` y `src/server.ts` ya existían. La aplicación montaba CORS, `express.json()`, `GET /health` y Swagger UI con una especificación mínima. La conexión Prisma estaba definida en `src/config/prisma.ts`. Todavía faltaban los middlewares globales de errores, la gestión del ciclo de vida de Prisma desde el servidor y la especificación completa de las 13 operaciones funcionales.

**Alcance:**

- Completar el registro de middlewares y el manejo global de errores.
- Conectar y gestionar Prisma desde el arranque y cierre del servidor.
- Mantener `GET /health`.
- Completar OpenAPI para las 13 operaciones funcionales, sin implementar todavía sus rutas.
- Integrar el documento OpenAPI completo con Swagger UI.

**Registro de implementación**

- **Qué hicimos:**
  - Incorporamos un middleware para responder con JSON y HTTP 404 cuando se solicita una ruta inexistente.
  - Incorporamos un middleware centralizado para manejar JSON malformado y errores internos.
  - Configuramos el arranque del servidor para conectar Prisma antes de comenzar a escuchar solicitudes HTTP.
  - Configuramos el cierre ordenado del servidor y la desconexión de Prisma al recibir señales `SIGINT` o `SIGTERM`.
  - Añadimos el documento OpenAPI completo con las 13 operaciones funcionales definidas en la arquitectura.
  - Documentamos los esquemas de solicitudes y respuestas, parámetros, códigos de error y seguridad JWT previstos para las operaciones.
  - Integramos el documento OpenAPI con Swagger UI en `/api/docs`.
  - Conservamos `GET /health` como endpoint de infraestructura.

- **Cómo lo hicimos:**
  - Creamos `src/middlewares/not-found.middleware.ts` para manejar rutas no encontradas.
  - Creamos `src/middlewares/error-handler.middleware.ts` para centralizar errores.
  - Modificamos `src/app.ts` para registrar CORS, JSON, health, Swagger y los middlewares en el orden correspondiente.
  - Modificamos `src/server.ts` para importar Prisma, ejecutar `prisma.$connect()` antes de iniciar Express y ejecutar `prisma.$disconnect()` durante el cierre.
  - Creamos `src/docs/openapi.ts` como documento central de especificación OpenAPI.
  - Configuramos Swagger UI para utilizar `openApiDocument`.

- **Archivos creados o modificados:**
  - `src/app.ts` (modificado).
  - `src/server.ts` (modificado).
  - `src/middlewares/not-found.middleware.ts` (creado).
  - `src/middlewares/error-handler.middleware.ts` (creado).
  - `src/docs/openapi.ts` (creado).
  - `src/config/prisma.ts` (utilizado; no fue creado ni modificado en esta etapa).

- **Comandos ejecutados:**
  - `pnpm typecheck` (después de implementar el ciclo de vida de Prisma en `server.ts`).
  - `pnpm dev` (inicio de la API).
  - `curl -i http://localhost:3000/health` (comprobación de health).
  - `pnpm typecheck` (después de integrar OpenAPI en `app.ts`).
  - `pnpm build`.
  - `kill -INT <PID>` (prueba dirigida de la señal `SIGINT` al proceso Node que ejecutaba el servidor).

- **Verificaciones realizadas:**
  - `pnpm typecheck` terminó sin errores después de implementar el ciclo de vida de Prisma.
  - `pnpm dev` mostró `Database connected successfully` y `API listening on port 3000`.
  - `GET /health` respondió HTTP 200 con `{"status":"ok"}`.
  - La interfaz de Swagger en `/api/docs/` respondió HTTP 200 y se comprobó visualmente en el navegador que cargaba la documentación de las 13 operaciones funcionales.
  - `pnpm typecheck` terminó sin errores después de integrar `openApiDocument` en `app.ts`.
  - `pnpm build` terminó sin errores.
  - Se comprobó la respuesta JSON 404 de una ruta inexistente.
  - Se comprobó la respuesta JSON 400 ante un cuerpo JSON malformado.
  - Se provocó temporalmente un error interno y se comprobó la respuesta JSON 500; la ruta temporal de prueba fue retirada posteriormente.
  - Al enviar `SIGINT` directamente al proceso Node, se observaron los mensajes de cierre del servidor y `Database connection closed`.

- **Resultado:**
  - La base del servidor Express, el manejo global de errores y la documentación OpenAPI quedaron implementados.
  - Las comprobaciones de tipos, compilación, health, Swagger y respuestas de error descritas arriba fueron satisfactorias.
  - La etapa queda **implementada con verificación parcial**. No se declara cerrada hasta completar la revisión de comprobaciones y documentación prevista para el cierre de la etapa.

- **Problemas encontrados y soluciones:**
  - Al presionar `Ctrl+C` desde la terminal que ejecutaba `tsx watch`, la señal no llegó al proceso Node hijo de la forma esperada y no se observaron los mensajes de cierre.
  - Para comprobar el manejador, se identificó el PID del proceso Node y se le envió `SIGINT` directamente desde otra terminal. En esa prueba se observaron `SIGINT received. Shutting down...` y `Database connection closed`.
  - Por lo tanto, quedó comprobado el manejador cuando el proceso Node recibe `SIGINT` directamente; el comportamiento del cierre a través del supervisor `tsx watch` no se da por verificado.
  - No se documenta todavía una prueba de `SIGTERM` ni una prueba de fallo de conexión durante el arranque.

- **Decisiones técnicas:**
  - La conexión a PostgreSQL se establece antes de abrir el puerto HTTP para evitar iniciar la API sin conexión a la base de datos.
  - El cierre del servidor HTTP precede a la desconexión de Prisma.
  - El middleware 404 se registra después de las rutas y Swagger; el middleware de errores se registra al final.
  - El documento OpenAPI describe las 13 operaciones funcionales acordadas, pero su presencia en Swagger no significa que los endpoints estén implementados.
  - `GET /health` es un endpoint de infraestructura y no forma parte de las 13 operaciones funcionales.
  - Las rutas funcionales se implementarán en las etapas 5 y 6, según el plan.

- **Pendientes:**
  - Revisar y completar el manual de comprobaciones de la etapa.
  - Comprobar los casos adicionales de cierre y arranque que se consideren necesarios, incluyendo `SIGTERM` y fallo de conexión.
  - Confirmar el estado final de los documentos y preparar el commit de cierre de la etapa 3.

### Etapa 6. Operaciones funcionales
