## 1. Objetivo

Este documento describe los procedimientos para comprobar el funcionamiento de los componentes técnicos de Clínica Salud Integral durante su implementación.

Su propósito es disponer de una guía reproducible que permita verificar el entorno, las variables de configuración, TypeScript, Prisma, PostgreSQL, las migraciones, los datos iniciales, las relaciones entre entidades, el servidor Express y las operaciones funcionales.

Cada comprobación incluye:

- Objetivo de la comprobación.
- Comando u operación que debe realizarse.
- Resultado esperado.
- Estado de ejecución.
- Interpretación del resultado.
- Posibles problemas y acciones recomendadas.

Este documento complementa la bitácora `07.0_Implementacion.md`. La bitácora registra qué se construyó; este manual explica cómo comprobarlo.

## 2. Consideraciones generales

### 2.1. Ubicación del proyecto

Todos los comandos se ejecutan desde la raíz del proyecto:

```bash
cd ~/dev/FUNVAL/Sem\ 5/FUNVAL-pro5-prisma-clinica
```

Antes de ejecutar cualquier comprobación, confirmar que estamos en el directorio correcto:

```bash
pwd
```

### 2.2. Convenciones

- Los comandos `pnpm` se ejecutan desde la raíz del proyecto.
- No se deben compartir ni publicar los valores reales del archivo `.env`.
- Las comprobaciones no deben modificar datos de producción.
- No se deben repetir migraciones iniciales sobre una base de datos ya inicializada.
- Se debe distinguir entre una operación ejecutada correctamente y una funcionalidad verificada.
- Las pruebas que modifican datos deben utilizar una base de datos apropiada para pruebas.
- No se deben introducir rutas temporales de prueba en el código definitivo.

### 2.3. Interpretación de resultados

| Estado | Significado |
|---|---|
| Correcto | La comprobación terminó y produjo el resultado esperado. |
| Incorrecto | Se produjo un error o el resultado no coincide con lo esperado. |
| Pendiente | Todavía no se ha ejecutado la comprobación. |
| No aplica | La comprobación no corresponde a la etapa actual. |

## 3. Comprobaciones de preparación del entorno

### 3.1. Comprobar Node.js

**Objetivo:** confirmar que Node.js está instalado y disponible.

```bash
node --version
```

**Resultado esperado:** una versión compatible con el proyecto (Node.js >= 20.19.0).

**Estado registrado:** correcto. Se confirmó Node.js v22.23.4.

### 3.2. Comprobar pnpm

**Objetivo:** confirmar que el gestor de paquetes está disponible.

```bash
pnpm --version
```

**Resultado esperado:** versión `12.18.0`.

**Estado registrado:** correcto. Se confirmó pnpm 12.18.0.

### 3.3. Comprobar dependencias instaladas

**Objetivo:** verificar que las dependencias del proyecto se encuentran instaladas.

```bash
pnpm install --frozen-lockfile
```

**Resultado esperado:** finalización sin errores y sin cambios en el archivo de bloqueo.

Esta operación instala las dependencias fijadas por el archivo de bloqueo; no debe actualizarlo.

**Estado registrado:** correcto. La instalación de dependencias se completó durante la preparación del proyecto.

### 3.4. Comprobar PostgreSQL

**Objetivo:** verificar que el servicio de PostgreSQL está activo.

```bash
sudo systemctl status postgresql
```

**Resultado esperado:** el servicio debe aparecer como `active (running)`.

Para salir de la pantalla de estado se utiliza la tecla `q`.

**Estado registrado:** correcto. Se confirmó el entorno PostgreSQL 16.15.

### 3.5. Comprobar la protección de archivos sensibles

**Objetivo:** confirmar que los archivos locales con credenciales no se incorporan al repositorio.

```bash
git check-ignore .env
```

**Resultado esperado:** Git debe mostrar `.env` como archivo ignorado.

Comprobar que `.env.example` no esté ignorado:

```bash
git check-ignore .env.example
```

**Resultado esperado:** no debe mostrar una coincidencia de archivo ignorado.

La plantilla `.env.example` puede versionarse, pero nunca debe contener credenciales reales.

**Estado registrado:** correcto. La configuración del repositorio contempla `.env` como archivo ignorado y permite versionar `.env.example`.

### 4.2. Comprobar las variables de entorno

**Objetivo:** revisar que el esquema de validación contemple las variables requeridas.

Archivo:

```text

```

Variables esperadas:

| Variable | Validación |
|---|---|
| `DATABASE_URL` | URL válida y obligatoria. |
| `JWT_SECRET` | Cadena obligatoria, sin valor predeterminado y con longitud mínima de un carácter. |

No mostrar ni copiar los valores reales de `.env` durante esta revisión.

**Estado registrado:** correcto. Se confirmó la incorporación de `JWT_SECRET` como variable obligatoria en el esquema de validación.

3. El proceso devuelve el control a la terminal.

`--noEmit` indica que TypeScript realiza la comprobación sin generar archivos JavaScript.

**Estado registrado:** correcto. Se ejecutó satisfactoriamente durante la configuración inicial y nuevamente en revisiones posteriores.

## 5. Esquema de datos, migraciones y datos iniciales

### 5.1. Validar el esquema Prisma

**Objetivo:** comprobar que `schema.prisma` cumple las reglas de sintaxis y estructura de Prisma.

```bash
pnpm exec prisma validate
```

**Resultado esperado:**

```text
The schema is valid
```

La redacción exacta puede variar según la versión de Prisma.

Si aparece un error, revisar el archivo:

```text
prisma/schema.prisma
```

**Estado registrado:** correcto.

### 5.2. Generar Prisma Client

**Objetivo:** generar el cliente que permite utilizar los modelos de Prisma desde TypeScript.

```bash
pnpm exec prisma generate
```

**Resultado esperado:** mensaje de generación correcta y ubicación:

```text
./generated/prisma
```

La generación debe coincidir con el esquema actual.

**Estado registrado:** correcto. Se generó Prisma Client 7.10.1.

### 5.3. Comprobar el estado de las migraciones

**Objetivo:** comprobar si las migraciones locales están aplicadas en PostgreSQL.

```bash
pnpm exec prisma migrate status
```

**Resultado esperado:**

```text
1 migration found in prisma/migrations.
Database schema is up to date!
```

El número de migraciones puede aumentar conforme evolucione el proyecto.

Una migración aplicada debe aparecer registrada en la tabla `_prisma_migrations`.

**Estado registrado:** correcto. La base de datos se encontraba sincronizada con la migración inicial.

### 5.4. Consultar las migraciones en PostgreSQL

**Objetivo:** comprobar visualmente que PostgreSQL conserva el registro de la migración aplicada.

Procedimiento:

1. Iniciar Prisma Studio.
2. Seleccionar la tabla `_prisma_migrations`.
3. Revisar el campo `migration_name`.
4. Revisar `finished_at`.
5. Revisar `applied_steps_count`.

**Resultado esperado:**

- La migración `20261115014117_init` aparece registrada.
- `finished_at` contiene una fecha.
- `rolled_back_at` aparece como `NULL`.
- `applied_steps_count` es 1.

Esto permite comprobar que la migración inicial quedó registrada como aplicada.

**Estado registrado:** correcto. La migración inicial fue aplicada y se confirmó el estado sincronizado de la base de datos.

### 5.5. Ejecutar el seed

**Objetivo:** insertar los datos iniciales del catálogo de especialidades y médicos.

```bash
pnpm exec prisma db seed
```

El comando ejecuta:

```text
tsx prisma/seed.ts
```

**Resultado esperado:**

- Cinco especialidades.
- Dos médicos por especialidad.
- Diez médicos en total.
- Mensaje `Seed completado correctamente`.
- Mensaje de ejecución correcta del seed.

El seed utiliza operaciones `upsert` para identificar los registros existentes mediante sus campos únicos.

**Estado registrado:** correcto.

### 5.6. Comprobar la idempotencia del seed

**Objetivo:** verificar que ejecutar nuevamente el seed no genere registros duplicados.

Ejecutar por segunda vez:

```bash
pnpm exec prisma db seed
```

**Resultado esperado:**

- La operación termina correctamente.
- Se reconocen las mismas cinco especialidades.
- Se reconocen los mismos diez médicos.
- No se crean registros duplicados.

La idempotencia es importante porque permite ejecutar el seed repetidamente sin multiplicar los registros iniciales.

**Estado registrado:** correcto. La segunda ejecución se realizó correctamente y no generó duplicados.

### 7.8. Comprobar el cierre de Prisma mediante SIGINT

**Objetivo:** verificar que el servidor puede cerrar su conexión con PostgreSQL cuando recibe una señal de interrupción.

El servidor incorpora manejadores para:

- `SIGINT`
- `SIGTERM`

**Prueba realizada:**

Durante la ejecución de `pnpm dev`, se identificó el proceso Node que ejecutaba `src/server.ts` y se envió directamente la señal `SIGINT` desde otra terminal.

Comando utilizado:

```bash
kill -INT <PID>
```

Sustituir `<PID>` por el identificador real del proceso Node.

**Resultado observado:**

```text
SIGINT received. Shutting down...
Database connection closed
```

**Interpretación:** el manejador recibió la señal, inició el cierre del servidor HTTP y desconectó Prisma.

**Estado registrado:** correcto para la prueba de `SIGINT` enviada directamente al proceso Node.

**Limitación de la comprobación:** al utilizar `Ctrl + C` desde la terminal que ejecutaba `tsx watch`, no se observaron inicialmente los mensajes de cierre. La prueba satisfactoria se realizó enviando la señal directamente al proceso Node. Por tanto, no se considera verificado el comportamiento de cierre a través del supervisor `tsx watch`.

## 17. Atajos rápidos

Esta sección reúne el recorrido mínimo para iniciar la aplicación, consultar los datos y probar las rutas desde Swagger UI. Los comandos utilizan la conexión configurada en `DATABASE_URL`; antes de ejecutarlos, confirma que apunte al entorno local correcto. Las solicitudes de creación y actualización sí modifican esa base de datos.

### 17.1. Iniciar la API

Desde la raíz del proyecto, abre una terminal:

```bash
pnpm dev
```

El comando genera Prisma Client e inicia Express. Deja la terminal abierta. Cuando el servidor esté listo, debe mostrar que se conectó a PostgreSQL y que escucha en el puerto configurado, normalmente `3000`.

En otra terminal puedes comprobar la ruta de salud:

```bash
curl -i http://localhost:3000/health
```

**Resultado esperado:** HTTP `200` y `{"status":"ok"}`.

### 17.2. Abrir Swagger UI

En el navegador, visita:

```text
http://localhost:3000/api/docs/
```

Swagger UI permite consultar los contratos y ejecutar solicitudes HTTP con **Try it out** y **Execute**. En las rutas con parámetros, completa cada UUID o fecha antes de ejecutar la solicitud.

### 17.3. Iniciar sesión y autorizar Swagger

Las rutas protegidas requieren un JWT. Swagger usa el esquema Bearer definido en OpenAPI y agrega el prefijo `Bearer` al enviar la solicitud.

1. Abre `POST /api/auth/login` y selecciona **Try it out**.
2. Completa el correo y la contraseña de una cuenta de prueba existente en el cuerpo JSON, y selecciona **Execute**.
3. Comprueba que la respuesta sea HTTP `200` y copia el valor de `token` de la respuesta. No lo guardes en este documento ni lo compartas.
4. Selecciona **Authorize** en Swagger UI y pega únicamente el valor del token, sin escribir `Bearer` delante. Confirma con **Authorize** y cierra el diálogo.
5. Ejecuta las rutas protegidas con la cuenta y el rol correspondientes. Para probar otro rol, vuelve a hacer login con esa cuenta y reemplaza el token en **Authorize**.
6. Al terminar, selecciona **Logout** en el diálogo de autorización.

`POST /api/auth/login` es público. `POST /api/auth/register` requiere una cuenta GERENCIA; permite registrar RECEPCIONISTA o MEDICO, y para MEDICO necesita el UUID de un registro médico existente. Si todavía no existe una cuenta GERENCIA, el procedimiento de inicialización se documenta en la sección 8. Usa cuentas de prueba y no introduzcas credenciales reales en capturas o evidencias.

### 17.4. Abrir Prisma Studio

En una tercera terminal, desde la raíz del proyecto:

```bash
pnpm exec prisma studio
```

Abre la URL que muestre Prisma CLI (normalmente `http://localhost:5555`). Prisma Studio utiliza `DATABASE_URL`, igual que la aplicación. Puedes consultar pacientes, médicos, especialidades, citas y usuarios. Evita editar o eliminar registros si solo estás revisando información.

### 17.5. Las 13 rutas y su función

En Swagger, los parámetros de ruta aparecen entre llaves, por ejemplo `{id}`. En una solicitud directa también pueden escribirse como `:id` en la documentación de Express; para probarlas, reemplaza el marcador por un UUID existente.

| # | Método y ruta | Acceso | Función |
|---:|---|---|---|
| 1 | `POST /api/auth/login` | Público | Valida credenciales y devuelve un JWT de una hora. |
| 2 | `POST /api/auth/register` | GERENCIA | Crea cuentas RECEPCIONISTA o MEDICO; MEDICO debe vincularse con un registro `Doctor` existente y sin cuenta. |
| 3 | `POST /api/patients` | RECEPCIONISTA | Registra un paciente con datos validados. |
| 4 | `GET /api/patients` | RECEPCIONISTA | Devuelve el listado de pacientes. |
| 5 | `GET /api/patients/{id}` | RECEPCIONISTA | Devuelve los datos del paciente y su historial de citas, con médico y especialidad. |
| 6 | `GET /api/doctors` | RECEPCIONISTA | Lista médicos; acepta el filtro opcional `specialtyId`. |
| 7 | `GET /api/specialties` | RECEPCIONISTA | Devuelve el catálogo de especialidades. |
| 8 | `GET /api/doctors/me/patients/{patientId}` | MEDICO | Devuelve datos básicos y solo las citas que el paciente comparte con el médico autenticado. |
| 9 | `POST /api/appointments` | RECEPCIONISTA | Programa una cita futura para un paciente y médico existentes; rechaza coincidencias exactas de horario. |
| 10 | `GET /api/doctors/{id}/appointments?from=…&to=…` | MEDICO | Consulta la agenda propia en el intervalo `[from, to)`: inicio inclusivo y fin exclusivo. |
| 11 | `PATCH /api/appointments/{id}/status` | MEDICO propietario o RECEPCIONISTA | Cambia una cita PROGRAMADA a COMPLETADA o CANCELADA; RECEPCIONISTA puede hacerlo para cualquier médico y MEDICO solo para su propia agenda. GERENCIA no tiene acceso. |
| 12 | `GET /api/reports/appointments-by-specialty` | GERENCIA | Agrupa el total histórico de citas por especialidad. |
| 13 | `GET /api/reports/daily-cutoff?date=YYYY-MM-DD` | GERENCIA | Devuelve el conteo diario UTC de citas COMPLETADA y CANCELADA para la fecha indicada. |

> **Nota de documentación:** el comportamiento actual de `PATCH /api/appointments/{id}/status` permite RECEPCIONISTA además de MEDICO propietario. La descripción OpenAPI de esa operación aún indica acceso exclusivo de MEDICO; hay que alinear ese contrato en una actualización posterior.

### 17.6. Atajos para solicitudes directas con curl

Para pruebas puntuales desde terminal, define la dirección de la API:

```bash
API="http://localhost:3000"
```

Por ejemplo, consulta el catálogo de especialidades enviando un JWT obtenido con login:

```bash
curl -i "$API/api/specialties" \
  -H "Authorization: Bearer TOKEN_DE_LA_CUENTA_RECEPCIONISTA"
```

En `curl`, a diferencia del diálogo **Authorize** de Swagger, sí se escribe el prefijo `Bearer` antes del token. Sustituye el texto de ejemplo por el token vigente sin pegarlo en archivos o documentos.
