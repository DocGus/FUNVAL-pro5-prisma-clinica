# Clínica Salud Integral — Implementación

## 1. Objetivo

Documentar el proceso de implementación de Clínica Salud Integral, desde la preparación de la base de datos hasta las pruebas y entrega del proyecto.

Este documento funcionará como una bitácora técnica y progresiva. En cada etapa se registrarán las actividades realizadas, las decisiones técnicas, los archivos creados o modificados, los comandos ejecutados y las verificaciones efectuadas.

La documentación distinguirá entre:

- **Implementado:** funcionalidad desarrollada total o parcialmente; se indicará el alcance concreto.
- **Verificado:** funcionalidad comprobada mediante comandos o pruebas.
- **Pendiente:** actividad todavía no realizada. Una actividad implementada pero sin comprobación se marcará como implementada y pendiente de verificación.

### Etapa 5. Autenticación y autorización

**Objetivo:** habilitar el acceso seguro y limitar cada operación según el rol de la cuenta.

**Estado:** implementada y verificada manualmente. La cuenta inicial de GERENCIA se crea mediante un procedimiento de terminal; GERENCIA registra cuentas de RECEPCIONISTA y MEDICO.

**Qué quedó implementado:**

- `prisma/create-initial-manager.ts` solicita correo y contraseña en terminal interactiva, oculta la contraseña, normaliza el correo y almacena un hash bcrypt con costo 10. Si ya existe una cuenta GERENCIA, termina sin crear otra.
- `POST /api/auth/login` normaliza el correo, compara el hash y devuelve un JWT con vigencia de una hora.
- `POST /api/auth/register` requiere autenticación GERENCIA y permite crear solo RECEPCIONISTA o MEDICO. Para MEDICO requiere un `doctorId` existente y no vinculado a otra cuenta.
- La creación de la cuenta MEDICO y su vínculo con `Doctor` se realiza dentro de una transacción.
- `authenticate` valida el token y sus claims; `authorizeRoles` comprueba los roles permitidos.
- Los esquemas de usuario requieren contraseña de al menos ocho caracteres para registro y normalizan el correo con espacios externos eliminados y minúsculas.
- Las respuestas de registro exponen `id`, `email` y `role`; el token se obtiene mediante login. No se devuelve `passwordHash`.

**Componentes principales:**

- `prisma/create-initial-manager.ts`
- `src/schemas/user.schema.ts`
- `src/models/user.model.ts`
- `src/services/auth.service.ts`
- `src/controllers/auth.controller.ts`
- `src/routes/auth.routes.ts`
- `src/middlewares/auth.middleware.ts`
- `src/middlewares/role.middleware.ts`
- `src/types/express.d.ts`
- `src/docs/openapi.ts`

**Verificaciones registradas:** registro de RECEPCIONISTA y MEDICO con HTTP 201; login de los tres roles; rechazo sin token con HTTP 401; rechazo por rol no autorizado con HTTP 403. La suite automatizada también cubre autenticación y autorización con modelos simulados. El detalle de las pruebas manuales se encuentra en `docs/08.0_comprobaciones.md`, sección 8.

**Resultado:** completada. La restricción que impide registrar GERENCIA desde el endpoint está implementada; la prueba automatizada la cubre. La bitácora de comprobaciones señala que falta conservar una ejecución manual aislada con el código HTTP exacto como evidencia individual.

### Etapa 6. Operaciones funcionales

**Objetivo:** implementar las operaciones de recepción, consultorio y gerencia usando la arquitectura Route → Middleware → Controller → Service → Model → Prisma.

**Estado:** implementada y verificada manualmente por módulos. La cobertura automatizada de API usa mocks; no sustituye la integración real con PostgreSQL.

**Operaciones implementadas:**

- **Pacientes:** RECEPCIONISTA registra, lista y consulta expedientes; se validan UUID, correo y fecha de nacimiento. El servicio transforma una colisión de correo en HTTP 409.
- **Directorio:** RECEPCIONISTA consulta médicos, filtra por `specialtyId` y consulta el catálogo de especialidades.
- **Consulta médica compartida:** MEDICO solo puede consultar datos básicos de pacientes con los que tenga una cita; la respuesta no incluye el correo del paciente ni citas de otros médicos.
- **Citas:** RECEPCIONISTA programa para un paciente y médico existentes. Se rechaza una fecha pasada y se detecta una cita con el mismo instante para ese médico o paciente. El estado inicial es `PROGRAMADA`.
- **Agenda:** MEDICO consulta únicamente la agenda asociada a su cuenta. `from` es inclusivo, `to` exclusivo y ambos parámetros son obligatorios; se rechazan UUID, fechas o intervalos inválidos.
- **Estados:** MEDICO puede cambiar una cita propia desde `PROGRAMADA` a `COMPLETADA` o `CANCELADA`. Se rechazan citas ajenas, inexistentes o que ya estén finalizadas.
- **Reportes:** GERENCIA consulta el total histórico de citas por especialidad y un corte diario UTC con conteos de `COMPLETADA` y `CANCELADA`, incluyendo cero cuando no hay filas para un estado.

**Componentes principales:** schemas de pacientes, médicos, citas y reportes; modelos Prisma de las cinco entidades y reportes; servicios, controladores y rutas correspondientes; `src/app.ts`; y `src/docs/openapi.ts`.

**Verificaciones registradas:** las pruebas manuales de `docs/08.0_comprobaciones.md`, secciones 9–11, documentan casos válidos y de error con respuestas HTTP. Las pruebas automatizadas cubren las rutas mediante Supertest con modelos simulados y las consultas esperadas de los modelos mediante mocks de Prisma. `pnpm typecheck` y `pnpm build` figuran como correctos en la última revisión registrada.

**Resultado:** implementada. Las operaciones están montadas en Express y documentadas en Swagger. La prueba de persistencia contra PostgreSQL todavía no se ha realizado con una base de integración independiente.

#### Diferencias de requisitos que requieren resolución

Estas discrepancias no se deben presentar como funcionalidades terminadas hasta acordar cuál documento de requisitos prevalece:

- **Unicidad del correo de paciente:** `Patient.email` es único en Prisma y en la migración, y la API devuelve conflicto para correos duplicados. `docs/00.0_requirements.md` registra como decisión aprobada que el correo de paciente no sea único.

- **Seed:** el seed contiene cinco especialidades y diez médicos. Cumple el mínimo de tres especialidades y dos médicos por especialidad del material de curso, pero difiere de la decisión local de tres/seis. Además, el `upsert` de médicos actualiza nombre, apellido, correo y especialidad de registros existentes; la decisión local pide no sobrescribirlos.
- **Relación cuenta–médico:** el modelo impone `doctorId @unique`, por lo que una cuenta MEDICO por registro `Doctor`. La documentación local lo adoptó, mientras que el material FUNVAL indica que esa cardinalidad no debe inferirse como requisito del curso. Confirmar si se mantiene como ampliación del equipo.

## 4. Registro de decisiones técnicas

- Prisma 7 genera el cliente en `generated/prisma` y utiliza `@prisma/adapter-pg` (`PrismaPg`) para PostgreSQL.
- Las claves de las entidades son UUID. `Appointment.scheduledAt` se mapea a la columna `startAt`.
- La autenticación usa bcryptjs y JWT de una hora. El endpoint de registro no crea cuentas GERENCIA.
- Los correos de usuario se normalizan a minúsculas y se recortan antes de validar/consultar.
- La agenda usa el intervalo semiabierto `[from, to)`, expresado en fechas ISO 8601 con zona horaria.
- El conflicto de citas definido en el servicio es de coincidencia exacta del instante para el mismo paciente o médico. No hay una regla de duración/traslape general.
- El reporte diario agrupa por la fecha UTC de `scheduledAt` y el estado actual de las citas; no representa el momento histórico en que cambió el estado.
- La consulta de paciente compartido limita los datos al médico autenticado y no expone el correo ni citas de otros médicos.
- Las decisiones en conflicto con requisitos académicos o con `docs/00.0_requirements.md` se enumeran en la etapa 7 y requieren resolución antes del cierre.
