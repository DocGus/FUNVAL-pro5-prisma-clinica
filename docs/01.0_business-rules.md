Clínica Salud Integral — Reglas de negocio
1. Pacientes
- El correo electrónico debe tener un formato válido.
- La fecha de nacimiento no puede ser posterior a la fecha actual.
- El correo electrónico es obligatorio y no único.
2. Médicos y especialidades
- Cada médico debe pertenecer a una especialidad existente.
- Una especialidad puede existir aunque todavía no tenga médicos registrados.
- Los médicos y las especialidades se incorporarán mediante datos iniciales (seed). El directorio será de consulta y no contará con operaciones CRUD administrativas.
- La consulta del directorio de médicos y del catálogo de especialidades estará disponible únicamente para RECEPCIONISTA.
3. Citas
- Los valores de fecha y hora recibidos por la API deben usar ISO 8601 e incluir `Z` o un offset explícito. Se convierten a UTC para almacenarlos y compararlos con el instante actual en UTC.
- No se permite programar citas en fechas u horas pasadas.
- No se permite programar una cita si ya existe otra, en cualquier estado, con el mismo instante `scheduledAt` para el mismo médico o para el mismo paciente. La comparación se realiza después de convertir los valores a UTC. Esta regla solo impide coincidencias exactas; no define duración ni reglas generales de traslape.
- El paciente y el médico asociados a una cita deben existir previamente.
- El estado inicial de toda cita será PROGRAMADA y se asignará automáticamente.
- Solo se permiten los cambios PROGRAMADA → COMPLETADA y PROGRAMADA → CANCELADA. COMPLETADA y CANCELADA son estados finales.
4. Administración de cuentas
- El registro profesional de un médico será independiente de la creación de su cuenta de acceso.
- Las cuentas de MEDICO deberán vincularse obligatoriamente con un registro existente de `Doctor`.
- Cada cuenta MEDICO podrá vincularse a un solo registro de médico, y cada registro de médico podrá tener como máximo una cuenta vinculada.
- GERENCIA será responsable de crear todas las cuentas de acceso de RECEPCIONISTA y MEDICO.
- La primera cuenta GERENCIA se generará mediante un procedimiento controlado desde la terminal.
- Para crear una cuenta MEDICO, GERENCIA deberá vincularla con un registro existente de `Doctor`. No se creará un nuevo registro profesional durante el alta de la cuenta.
- El endpoint de registro no permitirá crear cuentas con rol GERENCIA.
- Las contraseñas recibidas en el registro deben tener al menos ocho caracteres, sin requisitos adicionales de composición.
- Antes de registrar o autenticar una cuenta, se eliminan los espacios externos del correo y se convierte a minúsculas. `User.email` conserva su restricción de unicidad. El modelo Prisma `User` corresponde a la tabla física `User` en la migración actual.
- La primera cuenta GERENCIA se crea con `pnpm exec tsx prisma/create-initial-manager.ts`. El comando solicita el correo y una contraseña oculta, almacena la contraseña con bcryptjs y se detiene sin modificar datos si ya existe una cuenta GERENCIA.

5. Reportes y consultas
- El reporte de citas por especialidad cuenta todas las citas históricas, sin importar su estado. No incluye especialidades sin citas y no recibe filtros.
- El corte diario agrupa las citas por la fecha UTC de `scheduledAt` y muestra el estado actual de cada cita. No representa los cambios de estado realizados durante ese día. Siempre devuelve los conteos de COMPLETADA y CANCELADA, incluso cuando sean cero.
- La agenda médica requiere `from` y `to`, ambos ISO 8601 con zona explícita. Rechaza con HTTP 400 los valores inválidos o cuando `from` es mayor o igual que `to`. El intervalo es `[from, to)`.
- Los listados ordenan pacientes por `id` ascendente y médicos por apellido, nombre e `id` ascendente.

6. Datos iniciales y alcance
- El seed contiene tres especialidades y seis médicos ficticios, dos por especialidad. Al ejecutarse varias veces, crea únicamente los registros faltantes usando claves de búsqueda estables y no sobrescribe registros existentes.
- No se implementan operaciones para eliminar registros durante este proyecto.

7. Estado y clasificación de implementación

Estas reglas son requisitos aprobados. La plantilla actual solo incluye `GET /health`; las validaciones, reglas de citas, autenticación, autorización y reportes siguen pendientes de implementación. El esquema define enums y relaciones, pero no implementa por sí solo las reglas de aplicación. La migración inicial declara `Patient.email` único, aunque el requisito de la sección 1 establece que no debe ser único; la contradicción queda pendiente de resolución.

El requisito del seed establece tres especialidades y seis médicos y que no se sobrescriban registros existentes. `prisma/seed.ts` contiene cinco especialidades y diez médicos y actualiza los campos de médicos existentes; esta diferencia queda pendiente de resolución.

| Regla | Clasificación | Evidencia actual |
|---|---|---|
| Evitar citas con el mismo instante para el mismo médico o paciente | Requisito aprobado; pendiente de implementación | Prisma/migración tienen índices no únicos y no hay rutas de citas en la plantilla. No existe garantía de unicidad en base de datos. |
| Un médico solo consulta/modifica su propia agenda y sus citas | Requisito aprobado; pendiente de implementación | `User.doctorId` permite modelar el vínculo, pero aún no existen rutas ni controladores de agenda/propiedad. |
| Transiciones `PROGRAMADA` → `COMPLETADA` o `CANCELADA`, y estados finales | Requisito aprobado; pendiente de implementación | El enum y el default `PROGRAMADA` están en Prisma; no hay lógica que aplique transiciones válidas. |
| No aceptar citas pasadas ni fechas de nacimiento futuras | Requisito aprobado; pendiente de validación de aplicación | Prisma modela `scheduledAt` como `TIMESTAMPTZ(6)` y `birthDate` como `DATE`; los tipos no validan los límites de fecha/hora. |
| Restringir operaciones por rol | Requisito aprobado; parcialmente modelado | `UserRole` está definido en Prisma; no existen middleware ni rutas de negocio que autoricen roles en la plantilla. |
| Mantener tres especialidades/seis médicos y no sobrescribir datos existentes | Requisito aprobado; seed actual no coincide | El seed contiene cinco especialidades/diez médicos y actualiza médicos existentes encontrados por `professionalLicense`. |
