Clínica Salud Integral — Diagrama entidad-relación
1. Objetivo
Representar gráficamente la estructura de la base de datos de Clínica Salud Integral, identificando las entidades, sus atributos, las claves principales y foráneas, y las relaciones con sus respectivas cardinalidades.
2. Diagrama entidad-relación

El diagrama representa entidades y tablas físicas con nombres plurales. En Prisma, los modelos correspondientes serán singulares: `Patient`, `Doctor`, `Specialty`, `Appointment` y `User`. Esta diferencia de nombres no cambia las relaciones ni los campos.
```mermaid
erDiagram
    SPECIALTIES ||--o{ DOCTORS : clasifica
    DOCTORS ||--o{ APPOINTMENTS : atiende
    PATIENTS ||--o{ APPOINTMENTS : solicita
    USERS o|--o| DOCTORS : se_vincula

    PATIENTS {
        Int id PK
        String firstName
        String lastName
        String email
        Date birthDate
    }

    DOCTORS {
        Int id PK
        String firstName
        String lastName
        Int specialtyId FK
        Int userId FK, UK, nullable
    }

    SPECIALTIES {
        Int id PK
        String name
    }

    APPOINTMENTS {
        Int id PK
        Int patientId FK
        Int doctorId FK
        DateTime scheduledAt "timestamptz(3)"
        String reason nullable
        AppointmentStatus status
    }

    USERS {
        Int id PK
        String email UK
        String password
        Role role
    }
```
3. Descripción de las relaciones y cardinalidades
3.1 Specialty — Doctor
Cardinalidad: 1:N
- Una especialidad puede tener varios médicos registrados.
- Cada médico pertenece a una sola especialidad.
- Una especialidad puede existir aunque todavía no tenga médicos asociados.
3.2 Patient — Appointment
Cardinalidad: 1:N
- Un paciente puede tener varias citas registradas.
- Cada cita corresponde a un solo paciente.
- Un paciente puede existir sin tener citas registradas.
3.3 Doctor — Appointment
Cardinalidad: 1:N
- Un médico puede tener varias citas registradas.
- Cada cita corresponde a un solo médico.
- Un médico puede existir sin tener citas registradas.
3.4 User — Doctor
Cardinalidad: 1:0..1 (relación opcional uno a uno)
- Un médico puede existir sin una cuenta de acceso.
- Una cuenta de usuario puede estar vinculada como máximo a un único registro profesional.
- Toda cuenta con rol MEDICO deberá estar vinculada a un único registro del modelo Prisma `Doctor`.
- Las cuentas RECEPCIONISTA y GERENCIA no requieren una relación con el modelo Prisma `Doctor`.
- La relación es uno a uno y opcional en la base de datos. La aplicación debe exigir que todo usuario con rol MEDICO tenga un Doctor asociado; las cuentas GERENCIA y RECEPCIONISTA no requieren esa relación.
4. Resumen del diagrama

5. Consideraciones
- Las claves primarias identifican de manera única los registros de cada entidad.
- Las claves foráneas permiten establecer las referencias entre las tablas.
- La relación entre los modelos Prisma `User` y `Doctor` utiliza `userId` como clave foránea opcional y única. Sus tablas físicas son `users` y `doctors`.
- El modelo Prisma `Appointment` tendrá restricciones únicas compuestas en (doctorId, scheduledAt) y (patientId, scheduledAt). Estas restricciones impiden citas exactamente simultáneas para el mismo médico o paciente sin definir duración o traslapes.
- `Patient.birthDate` se almacena como `DATE`; los campos que representan instantes, incluido `Appointment.scheduledAt`, se almacenan como `timestamptz(3)` en PostgreSQL y usan `@db.Timestamptz(3)` en Prisma.
- Los valores enumerados AppointmentStatus y Role se mantienen definidos en el documento de entidades y modelo de datos.
- El diagrama representa la estructura lógica acordada y servirá como referencia para elaborar el modelo relacional en DBML.
