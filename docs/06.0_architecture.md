# Arquitectura del sistema
## Clínica Salud Integral

### 1. Objetivo y alcance

Definir las tecnologías, los componentes y el orden de implementación de la API REST de Clínica Salud Integral.

El proyecto contempla exclusivamente el desarrollo del backend. La API permitirá administrar pacientes, médicos, especialidades, citas y usuarios, mediante autenticación y permisos por roles.

### 3. Estructura y componentes del proyecto

#### 3.1. Arquitectura

Se utilizará una arquitectura modular MVC complementada con una capa de servicios.

Cada componente tendrá una responsabilidad específica:

| Componente | Responsabilidad |
|---|---|
| Routes | Definir los endpoints y asociarlos con sus controladores. |
| Middlewares | Validar solicitudes, autenticar usuarios y controlar permisos. |
| Controllers | Recibir solicitudes y generar respuestas HTTP. |
| Services | Ejecutar las reglas de negocio. |
| Models | Realizar consultas y operaciones mediante Prisma Client. |
| Schemas | Definir validaciones con Zod. |
| Config | Centralizar configuraciones y conexión a la base de datos. |
| Helpers compartidos | No se crea carpeta o capa adicional mientras las funciones pertenezcan a un servicio o middleware existente. |
| Tests | Verificar el funcionamiento del sistema. |

#### 3.2. Flujo de una solicitud

1. El cliente envía una solicitud HTTP.
2. Routes identifica el endpoint.
3. Middlewares ejecuta las validaciones y controles de acceso necesarios.
4. Controllers recibe la solicitud y llama al servicio correspondiente.
5. Services ejecuta las reglas de negocio.
6. Models realiza las operaciones mediante Prisma Client.
7. PostgreSQL almacena o devuelve la información.
8. Controllers envía la respuesta al cliente.

#### 3.5. Convenciones del contrato

- Las solicitudes y respuestas usarán JSON. Las fechas y horas se enviarán como cadenas ISO 8601 con `Z` u offset explícito; el parámetro `date` del corte diario usará el formato `YYYY-MM-DD`. La API convierte las fechas y horas recibidas a UTC antes de almacenarlas o compararlas. Las citas se comparan con el instante actual en UTC.
- Las respuestas exitosas devolverán directamente el objeto o arreglo indicado en cada operación, sin incluir contraseñas.
- Las operaciones protegidas requieren un JWT en el encabezado `Authorization: Bearer <token>`. Cada token tendrá una vigencia de una hora. No se implementarán refresh tokens. `JWT_SECRET` será obligatorio y se validará al iniciar la aplicación.
- `Patient.email` es obligatorio y no tiene restricción de unicidad. `User.email` sí es único; el modelo Prisma `User` corresponde a la tabla física `users`.
- Antes de registrar o autenticar una cuenta, se eliminan los espacios externos del correo y se convierte a minúsculas. El correo de paciente se valida y conserva obligatorio, sin exigir unicidad.
- Las contraseñas nuevas deben tener al menos ocho caracteres; no se aplican reglas adicionales de composición.
- El estado de una cita nueva será `PROGRAMADA`. Solo una cita en estado `PROGRAMADA` podrá cambiar a `COMPLETADA` o `CANCELADA`; ambos estados serán finales.
- No se acepta una cita si ya existe otra, en cualquier estado, con el mismo instante `scheduledAt` para el mismo médico o paciente. La comparación se realiza después de convertir los valores a UTC. La regla compara instantes exactos y no define duración ni traslapes.
- No se implementarán operaciones para eliminar registros.

Los modelos Prisma serán singulares: `Patient`, `Doctor`, `Specialty`, `Appointment` y `User`. Las tablas físicas serán plurales: `patients`, `doctors`, `specialties`, `appointments` y `users`; cada modelo se mapeará a su tabla mediante `@@map`. Esta convención solo afecta los nombres Prisma/SQL: no cambia las entidades, relaciones, campos ni operaciones de la API. Los campos camelCase `firstName`, `lastName`, `birthDate`, `specialtyId`, `userId`, `patientId`, `doctorId` y `scheduledAt` se mapearán a columnas `snake_case` mediante `@map`. Los demás nombres de columna conservarán su nombre actual. `Patient.birthDate` se almacenará como `DATE` en PostgreSQL (`@db.Date` en Prisma); los campos que representan instantes, incluido `Appointment.scheduledAt`, se almacenarán como `timestamptz(3)` (`@db.Timestamptz(3)` en Prisma).

`Appointment` tendrá `@@unique([doctorId, scheduledAt])` y `@@unique([patientId, scheduledAt])`. `doctorId` y `patientId` ya son obligatorios. Ambos índices cubren todos los estados; Prisma Client usará los atributos camelCase y el DDL resultante las columnas `doctor_id`, `patient_id` y `scheduled_at`.

Los errores usarán la estructura:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Descripción del error."
  }
}
```

Los códigos HTTP generales serán:

| Código | Uso |
|---|---|
| 200 | Consulta, inicio de sesión o actualización exitosa. |
| 201 | Recurso creado correctamente. |
| 400 | Solicitud, parámetro o dato inválido. |
| 401 | Falta autenticación válida o las credenciales de inicio de sesión no son válidas. |
| 403 | El rol autenticado no tiene permiso, o un médico intenta acceder a una agenda o cita ajena. |
| 404 | No existe el recurso solicitado, la relación asistencial requerida o una referencia, incluido `doctorId`. |
| 409 | Conflicto con el estado actual, correo de usuario duplicado, médico ya vinculado o cita exactamente simultánea para el mismo médico o paciente. |
| 500 | Error interno no esperado; no se expondrán detalles internos. |

JSON mal formado y cualquier validación de body, query o ruta responden 400. Un JWT ausente, inválido o expirado responde 401. Un rol insuficiente o la propiedad de un recurso ajeno responde 403. Un identificador sintácticamente válido pero inexistente responde 404. No se revelan detalles de excepciones en 500.

El campo `error.code` usará estos valores estables:

| HTTP | `error.code` |
|---|---|
| 400 | `VALIDATION_ERROR` |
| 401 | `AUTHENTICATION_ERROR` |
| 403 | `FORBIDDEN` |
| 404 | `NOT_FOUND` |
| 409 | `CONFLICT` |
| 500 | `INTERNAL_ERROR` |

El middleware de errores traducirá `PrismaClientKnownRequestError` con código `P2002` a HTTP 409 en el registro y al programar citas. Para citas, la restricción que produjo el error puede ser cualquiera de las dos combinaciones únicas. `P2025`, cuando corresponda a una operación que requiere un registro existente, se traduce a 404. Los errores desconocidos responden 500 con un mensaje genérico. Los casos de propiedad médica (403) y estado final de cita (409) se detectan en el servicio antes de formar la respuesta.

#### 3.6. Solicitudes y respuestas por operación

Las siguientes estructuras describen los campos de entrada y salida. Las propiedades indicadas como opcionales pueden omitirse.

**Autenticación**

| Método y endpoint | Acceso | Request | Response exitosa |
|---|---|---|---|

La contraseña requiere al menos ocho caracteres. El correo se normaliza antes de guardar. | 201: `{ "id": 1, "email": "usuario@clinica.test", "role": "RECEPCIONISTA" }`. Errores relevantes: 400, 401, 403, 404 si `doctorId` no existe, 409 si el correo ya existe o el médico ya tiene una cuenta. |
| `POST /api/auth/login` | Público | `{ "email": "usuario@clinica.test", "password": "contraseña" }`. El correo se normaliza antes de buscar la cuenta. | 200: `{ "token": "<JWT>" }`. Errores: 400 si los campos faltan o son inválidos; 401 si no coinciden las credenciales. |

El expediente médico compartido también requiere MEDICO.

#### 3.8. Definición del corte diario UTC

El reporte de corte operativo diario utilizará el campo `scheduledAt` de las citas y recibirá una fecha mediante el parámetro `date`, con formato `YYYY-MM-DD`.

El reporte agrupa las citas por la fecha UTC de `scheduledAt` y muestra el estado actual de cada cita. No representa los cambios de estado realizados durante ese día.

El periodo consultado se definirá mediante el siguiente intervalo:

- Inicio: 00:00:00 UTC del día indicado (incluido).
- Final: 00:00:00 UTC del día siguiente (excluido).

El reporte contabilizará las citas por estado:

- COMPLETADA.
- CANCELADA.

El intervalo permitirá incluir todas las citas correspondientes al día solicitado, sin duplicar registros entre días consecutivos.

El reporte por especialidad no aplica rango de fechas ni filtro de estado: cuenta todas las citas históricas. El corte diario responde siempre con `COMPLETADA` y `CANCELADA`, asignando cero a los estados sin coincidencias.

### 8. Criterio de implementación

Cada solicitud seguirá el flujo:

`Route → Middleware → Controller → Service → Model → Prisma → PostgreSQL`

Las rutas conectan componentes; middlewares autentican, autorizan y validan; controllers manejan HTTP; services aplican reglas de negocio; models contienen consultas Prisma. Se mantiene este patrón sin crear una carpeta `utils` hasta que exista una función auxiliar realmente compartida.

La implementación respeta los cinco modelos y sus restricciones, permisos por rol, reglas de UTC, las 13 operaciones y el conjunto de dependencias declarado. No se implementan DELETE, paginación, duración de citas ni horarios laborales.
